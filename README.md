# restaurant — メニューオーダーシステム（仮版）

飲食関係の悩み解決プロジェクトの第1弾として作った、飲食店スタッフがタブレットで操作する注文システムの仮版です。
1台のサーバーに**複数の店舗**を登録でき、店舗ごとにメニュー・注文・設定を分けて管理します。

- **店舗**: 人数入力 → メニュー選択（カテゴリ・おすすめ）→ 注文確認 → 注文確定（SQLite に保存）→ 会計（合計・割り勘の参考金額・支払い記録）→ 注文履歴
- **店舗アカウント**: 運営者からの招待メールに書かれた認証コードを入力し、パスワードを設定。以後はメールアドレス＋パスワードでログイン
- **運営者サイト**: 登録店舗の一覧（状態・最終ログイン・注文数）、店舗の招待・利用停止、全体のバックアップと復元

## 使用技術と採用理由

| 部分 | 技術 | 理由 |
| --- | --- | --- |
| サーバー | Python 3.11 以上の標準ライブラリのみ（`http.server` / `sqlite3` / `csv` / `hashlib` / `smtplib`） | 追加インストール不要で、PCに置くだけで動く。依存ライブラリの更新・脆弱性管理が不要 |
| データベース | SQLite（Python 同梱） | 1ファイルで管理でき、トランザクション・外部キー・制約が使える |
| メール | SMTP（Gmail のアプリパスワードなど**無料**のもの） | 有料のメール配信サービスを使わずに認証コードを送れる |
| 画面 | HTML / CSS / JavaScript（ES Modules、ビルド不要） | フレームワークなしで軽く、タブレットのブラウザでそのまま動く |
| テスト | Python `unittest`、Node.js 組み込みの `node --test` | どちらも追加インストール不要 |

外部ライブラリ・外部API・CDN は一切使っていません。費用がかかるサービスも使っていません。

- Python 3.11 以上（開発・動作確認は Python 3.14.5 / SQLite 3.50.4 / Windows 11）

## はじめての準備

### 1. メール送信の設定（無料・任意）

認証コードをメールで送るには、SMTP を環境変数で設定します。**設定しない場合は「開発モード」**になり、認証コードはサーバーを動かしているターミナル画面にだけ表示されます（メールは送られません。ログファイルにも残しません）。

Gmail（無料）の例:
1. Google アカウントで2段階認証をオンにし、「アプリ パスワード」を作成する（16文字）
2. PowerShell で次を設定してから起動する

```
$env:RESTAURANT_SMTP_HOST="smtp.gmail.com"
$env:RESTAURANT_SMTP_PORT="587"
$env:RESTAURANT_SMTP_USER="あなたのアドレス@gmail.com"
$env:RESTAURANT_SMTP_PASSWORD="アプリパスワード16文字"
$env:RESTAURANT_MAIL_FROM="あなたのアドレス@gmail.com"
py run.py
```

- 通信は必ず暗号化します（STARTTLS。`RESTAURANT_SMTP_SECURITY=ssl` でポート465の SSL も可）。暗号化できないサーバーには送りません。
- アプリパスワードはソースコードやファイルに書かず、環境変数で渡してください。

### 2. 運営者アカウントの作成（サーバーのPCで1回だけ）

```
py run.py create-operator
```

メールアドレスとパスワード（12文字以上）を入力します。同じメールアドレスでもう一度実行するとパスワードの再設定になります。

### 3. 起動して店舗を招待する

```
py run.py
```

1. サーバーのPCのブラウザで `http://localhost:8000/operator` を開き、運営者としてログイン（パスワード → メールの8桁コード）
2. 「店舗を招待する」に店舗名と担当者のメールアドレスを入れて「招待メールを送る」（サンプルメニュー付きで登録されます）
3. 店舗の担当者は届いたメールの認証コードを `http://<サーバー>:8000/account` で入力し、パスワード（10文字以上）を設定
4. 以後、店舗は `http://<サーバー>:8000/`（注文画面）または `/admin`（店舗管理）にメールアドレス＋パスワードでログイン

- **停止**: 起動したターミナルで `Ctrl + C`。
- パスワードを忘れた店舗は、ログイン画面の「初めて設定する方・パスワードを忘れた方」から同じ手順で再設定できます。

### 起動オプション（環境変数）

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `RESTAURANT_HOST` | `127.0.0.1` | `0.0.0.0` にすると同じ Wi-Fi の他のタブレットからも `http://<PCのIPアドレス>:8000/` で使えます（`RESTAURANT_ALLOWED_HOSTS` にその IP を追加） |
| `RESTAURANT_PORT` | `8000` | 使用するポート |
| `RESTAURANT_DATA_DIR` | `./data` | DB・ログ・バックアップ・秘密鍵の保存先 |
| `RESTAURANT_PUBLIC_URL` | `http://localhost:<ポート>` | 招待メールに書く設定ページのURL（例: `http://192.168.1.10:8000`） |
| `RESTAURANT_SMTP_*` / `RESTAURANT_MAIL_FROM` | なし | メール送信（上記） |
| `RESTAURANT_SECRET_KEY` | なし | 認証コード用の秘密鍵（32文字以上）。未指定なら `data/secret.key` を自動作成 |
| `RESTAURANT_SECURE_COOKIES` | なし | HTTPS で公開する場合に `1`（Cookie に Secure、HSTS を付ける） |
| `RESTAURANT_OPERATOR_ALLOW_REMOTE` | なし | `1` にするとサーバー以外のPCからも運営者サイトを使える（**非推奨**） |
| `RESTAURANT_BACKUP_DIR` | なし | バックアップ先（運営者サイトでも設定可） |
| `RESTAURANT_NO_LOGIN` | なし | `1` で**お試し用のログインなしモード**（このPCの localhost からのみ・最初に登録された店舗として操作・運営者サイトもログイン不要）。`RESTAURANT_HOST` が 127.0.0.1 以外だと起動しません。本番では使わないこと |
| `RESTAURANT_ALLOWED_HOSTS` | なし | 受け付けるホスト名・IPを `,` 区切りで追加（LAN の IP で使う場合に必要。例: `192.168.1.10`） |

LAN に公開する場合、通信は暗号化されない（HTTP）ため、店舗内の信頼できるネットワークだけで使ってください。インターネットに公開する場合は、HTTPS 化（リバースプロキシ）と `RESTAURANT_SECURE_COOKIES=1` が必須です。

## アカウントと権限

| 種類 | ログイン方法 | できること |
| --- | --- | --- |
| 店舗（注文画面） | メールアドレス＋パスワード | 注文・会計・支払い記録・状態更新・自店舗の注文履歴 |
| 店舗（管理機能） | 上記＋**15分以内のパスワード再入力** | 店舗設定・カテゴリ・商品・CSV入出力・注文取消・自店舗の操作ログ |
| 運営者 | メールアドレス＋パスワード＋**メールの認証コード**（毎回）。既定でサーバー本体からのみ | 登録店舗の一覧・招待・利用停止/再開、全体のバックアップと復元、全体の操作ログ |

- 店舗は**自店舗のデータしか見られません**（他店舗の注文IDを指定しても「見つからない」扱い）。運営者も店舗の注文操作はできません。
- ログインの有効期限: 店舗は操作がないまま12時間（最長24時間）、運営者は30分（最長8時間）。サーバーを再起動すると全員ログアウトします。

## 画面と操作の流れ（店舗）

1. **ログイン**: メールアドレスとパスワード。
2. **トップ**: 店舗名と人数入力。空欄・0・マイナス・小数・文字・最大人数（既定30人、管理画面で変更可）超えは日本語の理由と直し方を表示して先へ進みません。人数を入れただけでは注文は確定しません。
3. **メニュー**: 「★おすすめ」とカテゴリのタブ、商品カード（仮画像・商品名・価格・販売状態・数量の −/＋）、右側（縦画面では画面下）にカート。数量が 0 になった商品はカートから消えます。「削除」は「元に戻す」で取り消せます。販売停止商品は注文できません。
4. **注文確認**: 商品・単価・数量・小計・合計・人数を表示。「メニューに戻って修正」か「この内容で注文を確定する」。
5. **注文完了**: 注文番号（例: `20261019-0001`）を表示。再読み込みしても二重登録されません。
6. **会計**: 保存済みの注文から合計・1人あたりの参考金額を計算して表示。「会計内容を確認しました」→「代金の受け取りを記録する」（確認ダイアログあり）の2段階で、自動で支払い済みにはなりません。
7. **注文履歴**: 日付・注文番号で検索。状態の更新（受付→調理中→提供済み）、会計画面を開く、取消（パスワードの再入力が必要）。

## 仮仕様（仕様書で決まっていなかった部分）

| 項目 | 仮版での決め方 |
| --- | --- |
| 金額 | 円単位の整数。表示価格は**税込**とみなし、税計算はしない |
| 1人あたりの参考金額 | `合計 ÷ 人数` の **1円未満切り捨て**。端数（例: 1,000円÷3人 → 333円、端数1円）は画面に明示し、誰かの分に加えて調整してもらう。人数が1未満なら計算しない |
| 注文の単位 | 1回の確定 = 1注文。同じお客様の追加注文は新しい注文として登録する |
| 数量 | 1商品につき 1〜99、1注文 50 種類まで |
| 注文状態 | 受付 → 調理中 → 提供済み（順番にのみ進める）、取消 |
| 支払い状態 | 未会計 → 会計確認済み → 支払い済み、取消 |
| 取消 | パスワードの再入力が必要。理由必須。データは削除せず「取消」として残し、操作ログに記録。**支払い済みの注文は取消・変更不可**（権限・返金の仕組みが未実装のため） |
| 売上の集計 | 取消注文は**含めない**。「売上合計」は取消以外の注文合計、「支払い済み合計」は代金受け取りを記録した注文のみ |
| 注文番号 | `YYYYMMDD-連番4桁`（店舗ごと・日本時間の日付ごと） |
| 日時 | 日本時間の ISO 8601（例: `2026-10-19T14:10:00+09:00`）で保存 |
| おすすめの好み入力 | 年齢層（お子さま / 10〜20代 / 30〜50代 / 60代以上）、辛いもの・甘いもの・軽め、好きなカテゴリ。すべて任意で、**DB には保存しない** |

## おすすめのルール（外部AIは不使用）

商品ごとに `人気度(0〜100) × 0.3` を基本点とし、次を加点します。

| 条件 | 加点 | 表示される理由 |
| --- | --- | --- |
| 「辛いもの」を選び、商品タグに `spicy` | +40 | 辛いものがお好きな方に |
| 「甘いもの」を選び、`sweet` | +40 | 甘いものがお好きな方に |
| 「軽め」を選び、`light`（`hearty` は −15） | +40 | 軽めのお食事に |
| 好きなカテゴリと一致 | +25 | お好みの「○○」から |
| 年齢層タグ（`age_child` など）と一致 | +10（参考程度） | ○○に好評 |
| 人気度 70 以上 | — | 人気商品 |

- 販売停止・非表示カテゴリの商品はおすすめしません。お子さま・10〜20代を選んだ場合は `alcohol` タグの商品を除きます。
- 同じカテゴリは最大2品までにして偏りを防ぎ、6品を表示します。条件なし・一致なしの場合は人気順です。
- おすすめの取得に失敗しても、通常のカテゴリから注文できます（画面には人気商品を表示）。

使えるタグ: 半角小文字英数字と `_`（例: `spicy`, `sweet`, `light`, `hearty`, `kids`, `alcohol`, `age_child`, `age_youth`, `age_adult`, `age_senior`）。CSV では `;` 区切りで1商品10個まで。

## データの保存場所

```
data/                  ← Web には公開されない（static/ の外）。Git 管理外
├─ restaurant.db       ← 正式なデータ（SQLite、WALモード、全店舗分）
├─ secret.key          ← 認証コード用の秘密鍵（自動作成。DB・バックアップには含まれない）
├─ logs/app.log        ← 動作ログ・エラーログ（1MB×5世代。パスワード・認証コードは書かない）
└─ backups/            ← バックアップ（既定の保存先）
```

`data/` フォルダは、サーバーを動かすPCの管理者以外が読めない場所に置いてください。

### テーブル

| テーブル | 内容 |
| --- | --- |
| `stores` | 店舗アカウント（店舗名・メールアドレス・パスワードのハッシュ・状態・ログイン失敗回数・ロック期限） |
| `operators` | 運営者アカウント（メールアドレス・パスワードのハッシュ・ロック情報） |
| `verification_codes` | 認証コード（**HMAC 値のみ**。有効期限・試行回数・使用済み） |
| `categories` / `products` | 店舗ごとのカテゴリ・商品（`store_id` で区別） |
| `orders` / `order_items` | 店舗ごとの注文・注文明細（注文時の商品名・単価のスナップショット。`小計 = 単価 × 数量` を制約で保証） |
| `store_settings` | 店舗ごとの設定（最大人数・CSVのBOM既定） |
| `settings` | 全体の設定（バックアップ先） |
| `audit_logs` | 操作ログ（ログイン・ロック・招待・パスワード設定・注文・会計・取消・設定変更・CSV取込・復元など） |
| `schema_migrations` | 適用済みマイグレーション |

- 他店舗のカテゴリを商品に付ける、他店舗の注文に明細を付ける、といったことは複合外部キーで DB 自体が拒否します。
- 確定済み注文の金額・人数と注文明細は、DB のトリガーで変更・削除できないようにしています。商品の価格を変えても過去の注文金額は変わりません。

### スキーマの変更（マイグレーション）

`app/migrations/` に `0003_説明.sql` のような連番ファイルを追加すると、次回起動時に未適用のものだけが1ファイル1トランザクションで適用されます（適用中は外部キー検査を止め、最後に `foreign_key_check` で整合性を確認）。適用済みのファイルは書き換えないでください。

旧版（単一店舗・管理者パスワード1つ）の DB は、起動時に `0002` で自動的に移行され、既存のデータは「店舗ID 1（メール未設定）」になります。旧版の管理者パスワードは削除されるので、運営者サイトでこの店舗に「メールを設定して招待」してください。

## 商品画像

画像はまだ作っていません。商品の `image_path`（既定は `images/products/<商品ID>.jpg`）にファイルが無い・読み込めない場合は「画像準備中」の仮画像を表示し、注文操作はそのまま使えます。

画像を用意したら `static/images/products/P001.jpg` のように置くだけで表示されます（png / jpg / jpeg / webp。4:3 の比率推奨）。画像フォルダは全店舗で共通なので、店舗ごとに違う画像を使う場合は CSV で `image_path` を店舗ごとに別のファイル名にしてください。

## CSV

文字コードは UTF-8（BOM あり・なしどちらも可）。Excel では「CSV UTF-8（コンマ区切り）」で保存してください。

### メニューCSV（取り込み・書き出し共通）

見本: [`sample/menu_sample.csv`](sample/menu_sample.csv)

| 列名 | 必須 | 形式 |
| --- | --- | --- |
| `product_id` | ○ | 半角英数字・`-`・`_`、1〜32文字（例: `P001`）。既存IDなら更新、新しいIDなら追加 |
| `category_name` | ○ | 自店舗に登録済みのカテゴリ名（無いカテゴリはエラー。先に管理画面で追加） |
| `product_name` | ○ | 1〜60文字。他の商品と同じ名前は不可。先頭に `= + - @` は不可 |
| `price` | ○ | 0〜1,000,000 の整数（円） |
| `image_path` | ○（空欄可） | `images/products/ファイル名.jpg` の形式、または空欄 |
| `is_available` | ○ | `1` = 販売中、`0` = 販売停止 |
| `popularity_score` | ○ | 0〜100 の整数 |
| `recommendation_tags` | ○（空欄可） | `spicy;age_child` のように `;` 区切り |
| `description` | 任意 | 200文字まで。列が無い場合、既存商品の説明は変更しない |
| `allergens` | 任意 | アレルギー。`egg;milk;wheat` のようなコード、または `卵;乳;小麦` の日本語名を `;` 区切り。使える項目: 卵(egg)・乳(milk)・小麦(wheat)・えび(shrimp)・かに(crab)・そば(buckwheat)・落花生(peanut)・くるみ(walnut)・大豆(soy)・ごま(sesame)。列が無い場合、既存商品の値は変更しない |

**取り込み手順**: 店舗管理画面（/admin）→「メニューCSV取込」→ ファイルを選んで「内容を確認する」→ 追加・更新・変更なし・エラーの件数と一覧を確認 →「取り込む」。

検証内容: 必須列の不足・想定外の列・列の重複、列数の不一致、商品IDの形式・ファイル内の重複、存在しないカテゴリ、負数・小数・範囲外の価格やスコア、タグ・画像パスの形式、既存商品との商品名の衝突、UTF-8 以外の文字コード、1MB 超・2,000 行超のファイル。

**エラーが1件でもあると何も反映しません。** 反映も検証からやり直して1トランザクションで行うため、途中までしか更新されない状態にはなりません。

### 売上CSV・注文履歴CSV（書き出しのみ）

店舗管理画面（/admin）→「CSV出力」で期間（最大366日）と BOM の有無を選んでダウンロードします。1行 = 注文明細1件です。

| 列 | 内容 |
| --- | --- |
| 注文ID | 注文番号（例: `20261019-0001`） |
| 注文日時 | 日本時間 |
| 商品ID / 商品名 | 注文時の商品名 |
| 数量 / 注文時単価 / 小計 | 円 |
| 注文合計 / 利用人数 | |
| 注文状態 / 支払い状態 | 日本語 |
| 取消理由 | 注文履歴CSVのみ |

- **売上CSVは取消注文を含みません。** 注文履歴CSVは取消注文も含みます。
- `= + - @` やタブで始まる文字列の先頭には `'` を付け、Excel で数式として実行されないようにしています。
- CSV はバックアップの代わりになりません。データの保全には次のバックアップを使ってください。

## バックアップ

DB 全体（全店舗・全アカウント）のバックアップなので、**運営者だけ**が操作できます。

- **運営者サイト**（/operator）→「バックアップ」→「今すぐバックアップ」
- **コマンド**: `py run.py backup`（一覧は `py run.py list-backups`）

SQLite のオンラインバックアップ機能を使うため、営業中（サーバー起動中）でも整合性のとれたコピーになります。作成後に整合性チェックを行い、問題がなければ `restaurant-YYYYMMDD-HHMMSS.db` として保存します。保存先は既定で `data/backups/`、運営者サイトで USB メモリなど別ドライブの絶対パスに変更できます（Web公開フォルダ内・ネットワーク共有・ネットワークドライブは不可）。

バックアップにはパスワードのハッシュとメールアドレスが含まれます。持ち出す場合は鍵のかかる場所で保管してください（認証コード用の秘密鍵 `secret.key` は含まれません）。

## 復元

1. 運営者サイト →「バックアップ」で一覧から「この時点に復元」→ 確認欄に「復元」と入力。
   - またはサーバーを停止してから `py run.py restore restaurant-20261019-140000.db`
2. 復元前の現在のデータは自動で `restaurant-…-before-restore.db` として保存されます（元に戻したいときはこのファイルから復元）。
3. 復元元は**バックアップフォルダ内の、命名規則に合い、整合性チェックに通ったファイル**だけで、書き込み先は常に設定された `data/restaurant.db` です。別の DB ファイルを誤って上書きすることはありません。
4. 復元すると全店舗・全アカウントがその時点に戻り、全員ログアウトします。復元中は注文操作をしないでください。

## セキュリティ対策（実装済み）

### アカウント情報の保護
- パスワードは PBKDF2-SHA256（60万回）＋ランダムソルトでハッシュ化して保存。平文はどこにも保存・記録しません。
- 認証コード（**8桁**）とパスワード設定用トークンは、DB の外にある秘密鍵（`data/secret.key`）による HMAC だけを保存。DB やバックアップが漏れても、そこからコードを割り出せません。
- パスワード・認証コード・トークンはログファイル・操作ログ・画面の応答に出しません（メールアドレスもログでは `a***@example.com` のように伏せます）。
- パスワードの条件: 10文字以上（運営者は12文字以上）・128文字まで、よく使われるもの・メールアドレスを含むものは不可。

### 不正ログイン対策
- ログイン失敗の応答・応答時間は、アカウントの有無や利用停止かどうかで変えません（登録メールアドレスを探られないため）。
- 同じアカウントで5回失敗すると15分ロック（DB に記録）。照合前に試行を予約するので、同時に大量送信してもロックまでに試せるのは5回だけです。
- 接続元IPごとの回数制限（ログイン10回/15分など）。ログイン成功でもリセットしません。
- 認証コードは有効期限つき（招待24時間・再設定15分・運営者10分）、最新の1つだけ有効、1つにつき5回まで。24時間の失敗が1つの接続元で10回・1アカウント全体で30回に達すると、それ以上は受け付けません（アカウント全体の上限に達したら本人にメールでお知らせ）。再送は1分間隔・1時間5回まで。
- パスワードを設定・変更すると、そのアカウントの他のログインはすべて無効になり、登録メールアドレスにお知らせを送ります。別プロセス（CLI や復元）でパスワードが変わった場合も、次の操作でログアウトになります。
- 第三者にロックされ続けても、ログイン中の端末はそのまま使え、メールの認証コードでパスワードを再設定するとロックに関係なくログインできます。認証コードの上限まで使い切られた場合は、運営者サイトの「再設定メールを送る」でロックと失敗回数を解除して、登録済みのアドレスにコードを送れます（利用中の店舗のメールアドレスは運営者でも変更できません）。
- 管理機能は15分ごとにパスワードを再確認。再確認を5回続けて間違えるとログアウトします。
- 運営者は毎回メールの認証コードが必要（二段階認証）。運営者サイトは既定でサーバー本体からのみ、リバースプロキシ経由（転送ヘッダー付き）の接続は拒否します。

### 店舗間の分離・その他
- すべての店舗データは `store_id` で絞り込み、他店舗の注文は「存在しない」として扱います。DB の複合外部キーでも店舗をまたぐ関連付けを拒否します。
- 画面・API では全店舗共通の内部IDを使わず、店舗ごとの注文番号で注文を指定します（他店舗の注文数を推測されないため）。
- Cookie は `HttpOnly; SameSite=Strict`（HTTPS 公開時は `Secure` と HSTS）。状態を変える API は `X-Requested-With`・Origin・`Sec-Fetch-Site` を確認（CSRF 対策）。
- Host ヘッダーの許可リストで DNS リバインディング攻撃を防ぎます。LAN の IP アドレスで使う場合は `RESTAURANT_ALLOWED_HOSTS=192.168.1.10` のように追加するか、`RESTAURANT_PUBLIC_URL` を設定してください。
- 1接続あたりの受信時間の上限（合計20秒）と、同時接続数の上限（全体64・1台あたり8）で、接続を開きっぱなしにしたり少しずつ送り続けたりする攻撃によるサーバー停止を防ぎます。
- 入力値はすべてサーバー側で再検証。SQL はすべてパラメータ化。画面は `textContent` でのみ文字を表示し（`innerHTML` 不使用）、Content-Security-Policy で外部スクリプトを禁止。
- `data/`（DB・ログ・バックアップ・秘密鍵）とソースコードは配信対象外。パスの `..` などによる外部ファイル参照を拒否。バックアップ先にネットワーク共有（`\\サーバー\共有`）は指定できません。
- 内部エラーの詳細はログのみに出力し、画面にはエラー番号と日本語の案内だけを表示。
- 重要な操作（ログイン成功・失敗・ロック、招待、コード送信・失敗、パスワード設定、注文、会計、取消、設定変更、復元など）は `audit_logs` に記録。

### 自動テストで確認していること
`tests/test_accounts.py`・`tests/test_security_regressions.py`・`tests/test_server.py` で、アカウント列挙・総当たり（同時送信を含む）・コードの再利用や期限切れ・ロック・セッションの無効化・他店舗データへのアクセス・CSRF・パス・トラバーサル・Host 偽装・転送ヘッダー・不正な JSON・タイムアウト・同時接続数などを確認しています。独立したセキュリティ点検を繰り返し実施し、見つかった問題はすべて修正して再発防止テストを追加しました。

### 運用でお願いしたいこと
- SMTP を設定して開発モードを使わない（開発モードではコードがサーバーの画面に表示されます）。
- `data/` フォルダとバックアップは、サーバーPCの管理者だけが読める場所に置く（Windows ではフォルダのアクセス権で制限）。
- インターネットに公開する場合は HTTPS 化し、リバースプロキシで `/operator`・`/api/operator`・`/api/auth/operator` を外部から遮断する。**運営者サイトはプロキシ経由で公開しないこと**（転送ヘッダーを付けないプロキシだと、外部からの接続が 127.0.0.1 に見えてしまうため）。プロキシ経由では全員が同じ接続元IPに見えるので、接続元ごとの回数制限・同時接続数の制限も全員で共有になります。
- 運営者のメールアカウントにも2段階認証を設定する（メールが乗っ取られると認証コードも読まれるため）。

## 現在の制限事項

- 決済端末・レジ・キッチンプリンターとは連携していません（支払いは「受け取った」という記録のみ）。
- 店舗のアカウントは1店舗1つ（スタッフごとのアカウント・権限は未実装）。商品画像のフォルダは全店舗共通です。会計後の修正・返金も未実装です。
- ログイン状態と接続元ごとの回数制限はサーバーのメモリにあり、再起動するとリセットされます（アカウントのロックは DB に残ります）。
- HTTPS は内蔵していません。インターネットに公開する場合はリバースプロキシで HTTPS 化してください（その場合、接続元IPによる回数制限はプロキシのIPで数えられます）。
- SMTP 未設定の開発モードでは、認証コードがサーバーのターミナルに表示されます。本番運用では必ず SMTP を設定してください。
- 運営者がメールアドレスを使えなくなった場合の復旧は、サーバーのPCでの `create-operator` のみです。
- 追加注文を1つの伝票にまとめる機能はありません（別の注文番号になります）。
- 商品の新規追加・名前やタグの変更は CSV 取込で行います（管理画面で直接編集できるのは価格と販売状態のみ）。
- 縦向きタブレット・スマートフォン幅の表示は CSS で対応していますが、実機・狭い画面幅での目視確認はまだしていません（確認済みなのは横幅 約1270px のブラウザ）。
- 複数タブレットでの同時運用は自動テスト（同時送信）のみで、実機での確認はしていません。
